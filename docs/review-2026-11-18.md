# 交叉检查报告（2026-11-18）

> 方法：静态检查（ruff）、代码走查（安全/并发/错误路径）、运行时行为验证（测试 + 真实 PR）、
> 以及「主张 vs 实现」逐条核对。每条结论都带文件与行号，不写没有证据的判断。

## 一、总览

| 维度 | 现状 | 风险 | 结论 |
|---|---|---|---|
| 安全 | 变更类接口无鉴权；replay 可指定任意 clone_url；全局单 token | **高** | 本地/内网可用，公网部署前必须修 |
| 正确性 | 幂等/去重语义清晰，行号与投递有契约测试 | 低 | 本轮修掉多 worker 抢活问题 |
| 可靠性 | 队列降级、DB 兜底、失败可补发 | 中 | 缺自动重试与 Redis 断连恢复 |
| 性能 | 规则缓存、索引已补 | 中 | 单 worker 串行、无请求体上限 |
| 可观测性 | DB 聚合看板 + 结构化程度一般的日志 | 中 | 无 trace_id / 无 Prometheus 指标 |
| 数据 | create_all + 手写 migrate | 中 | 缺 Alembic，多人协作会漂移 |
| 测试 | 27 个契约测试，双数据库方言 | 低 | 缺并发/断连/HTML 转义等边界 |
| 交付 | CI 绿、Dockerfile/compose 就绪 | 中 | compose 因镜像拉取受限未完整验证 |
| 文档 | README/ADR/演示脚本/简历口径齐全 | 低 | 需持续防止「文档超前于实现」 |

## 四、明确不建议做的事

- **不要把 cel crawler/自动改代码塞进来**：评审只负责发现问题，自动修复是另一个产品（风险半径完全不同）。
- **不要为「架构好看」提前拆微服务**：单进程 + 队列已经能覆盖到数百 PR/天，拆分只会增加故障面。
- **不要在没有鉴权的情况下接公网 webhook**：这是当前最大风险，优先级高于任何功能。

## 五、结论

当前状态：**可演示、可写简历、可在内网试运行**；**不建议直接暴露公网**。
进入真实团队使用前，先把 P0 的四项（鉴权、clone_url 白名单、按仓库 token、prod 启动校验）做完，
再加 P1 的自动重试与断连恢复，整套系统才达到「可以交给别人运维」的标准。
